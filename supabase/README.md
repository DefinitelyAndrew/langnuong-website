# Reservation email setup (Gmail API)

The booking page uses Supabase Auth for email OTP generation and verification.
Supabase's Send Email Hook sends those OTP emails through Gmail's REST API. A
database trigger calls a separate Edge Function to send reservation confirmations,
cancellations, and reschedule notices. No SMTP password or email delivery vendor is
used.

## 1. Configure Google

1. In Google Cloud Console, select or create a project and enable **Gmail API**.
2. Configure the OAuth consent screen for the Gmail account that will send mail.
   Create an OAuth client with `https://developers.google.com/oauthplayground` as
   an authorized redirect URI. In [OAuth Playground](https://developers.google.com/oauthplayground),
   enable **Use your own OAuth credentials**, enter that client ID and secret,
   authorize the sender account for `https://www.googleapis.com/auth/gmail.send`,
   and exchange the code for a refresh token.
3. Keep the OAuth client ID, client secret, and refresh token. The authorized
   mailbox must match `GMAIL_FROM_EMAIL`.

Use a persistent consent-screen publishing status: external apps left in Testing
can have refresh tokens expire after seven days. Workspace accounts can use an
Internal consent screen. Google may require verification for the Gmail scope,
depending on how the app is configured.

## 2. Configure Supabase secrets

In **Project Settings → Edge Functions → Secrets**, add:

| Name | Value |
|---|---|
| `GMAIL_CLIENT_ID` | OAuth client ID |
| `GMAIL_CLIENT_SECRET` | OAuth client secret |
| `GMAIL_REFRESH_TOKEN` | Refresh token for the sending mailbox |
| `GMAIL_FROM_EMAIL` | Authorized Gmail address |
| `GMAIL_FROM_NAME` | Optional; defaults to `Lang Nuong Vietnam` |
| `RESERVATION_SITE_URL` | Optional; defaults to the current GitHub Pages site |
| `RESERVATION_EMAIL_WEBHOOK_SECRET` | A new, long random secret |

Supabase provides `SUPABASE_URL` and API secret keys to Edge Functions
automatically; do not add them as custom secrets. The RPC helper supports the
legacy `SUPABASE_SERVICE_ROLE_KEY` and the newer `SUPABASE_SECRET_KEYS` variable.

Also add `reservation_email_webhook_secret` with the same random value as
`RESERVATION_EMAIL_WEBHOOK_SECRET` in **Database → Vault**. This lets the database
authenticate its call to the reservation email function.

## 3. Deploy the Edge Functions

From the repository root, link the Supabase CLI to the project, then deploy:

```sh
supabase functions deploy send-reservation-email --no-verify-jwt
supabase functions deploy send-auth-email --no-verify-jwt
```

Both functions disable Supabase JWT verification because they validate their own
secrets: the reservation function checks its shared header secret, and the Auth
function verifies Supabase's signed webhook.

For the daily-limit update, install the SQL objects in step 5 before deploying
these revised functions; they call the database quota RPC.

The shared Gmail sender reserves each message against one atomic limit of 500
site-generated messages per Singapore calendar day. Once reached, reservation
confirmations, cancellation notices, and reschedule notices are queued for the
next day. OTP and account-security emails are not queued because their codes may
expire; those requests receive a retry-after-midnight error. Messages sent
manually from the Gmail mailbox do not use this site's counter.

## 4. Configure Supabase Auth OTP email

In **Authentication → Hooks**, enable the **Send Email** hook and select the
`send-auth-email` Edge Function. Copy the hook secret generated by Supabase into
the `SEND_EMAIL_HOOK_SECRET` Edge Function secret. Keep the Email provider enabled.
The function emails the OTP Supabase provides; `verifyOtp` remains responsible for
validating it. When Supabase supplies a token hash, the email also includes a
verification link for account signup and other link-based Auth flows.

Add this URL to **Authentication → URL Configuration → Redirect URLs** so the
reservation OTP flow can be identified and sent without a link:

```text
https://definitelyandrew.github.io/langnuong-website/reservations/exclusive1/?reservation-otp=1
https://definitelyandrew.github.io/langnuong-website/reservations/exclusive1/?reservation-otp=1&branch=langnuong1980s
https://definitelyandrew.github.io/langnuong-website/reservations/exclusive1/?reservation-otp=1&branch=bodevegetarian
```

## 5. Install the reservation email trigger

In **Database → Vault**, first create the `reservation_email_webhook_secret` secret.
If `public.reservations` does not exist yet, run `supabase/reservations.sql` first.
Then run `supabase/reservation-branches.sql` and `supabase/reservation-emails.sql`
in **SQL Editor**. The first adds the branch-aware booking RPC; the second
generates a private management token and sends email for Exclusive, Lang Nuong
Vietnam 1980's, and Bo De Vegetarian bookings, cancellations, and reschedules.
Re-run `reservation-emails.sql` when updating an existing project. It also
removes the old SMTP/duplicate guest-email triggers, creates the shared daily
quota and reservation email queue, and schedules its worker.

The booking flow must insert a row into `public.reservations` for the confirmation
trigger to run. Manage links are included when the inserted row has a `manage_token`.
The table currently permits anonymous inserts, so add server-side booking rate
limits and CAPTCHA verification before enabling these triggers on a public site;
otherwise a direct database insert could cause an email to an arbitrary address.

## 6. Sync reservations to the restaurant calendar

The `add-reservation-to-calendar` Edge Function routes each branch to its
configured Google Calendar. Share the Exclusive, 1980's, and Bo De calendars
with the Google service account as an editor and configure
`GOOGLE_SERVICE_ACCOUNT_KEY`. It uses the
`RESERVATION_EMAIL_WEBHOOK_SECRET` Edge Function secret and the matching
`reservation_email_webhook_secret` Vault secret from the email setup to authorize
the database request. Deploy with JWT verification disabled because the function
checks that shared secret itself:

```sh
supabase functions deploy add-reservation-to-calendar --no-verify-jwt
```

Then run (or re-run) `supabase/calendar-auto-add.sql` in the SQL Editor. It syncs
new bookings and reservation changes to the matching branch calendar, and removes
events when a booking is cancelled or deleted. Restaurant calendar events remain
one hour; online bookings allow up to 20 guests, use 30-minute slots, and require
at least three hours' notice.
The guest's own calendar buttons are independent of this restaurant-side sync.

## 7. Enable the daily email limit

Run (or re-run) `supabase/reservation-emails.sql` in the SQL Editor before
deploying the updated `send-auth-email` and `send-reservation-email` functions.
The SQL uses the existing `reservation_email_webhook_secret` Vault secret.
Queued reservation emails begin sending after midnight Singapore time, subject
to the next day's 500-message cap.

## 8. Verify

1. Open the Lang Nuong 1980's and Bo De reservation links from the website.
2. Request an OTP on each page and confirm the 8-digit code arrives.
3. Complete a booking for each branch and check its confirmation and restaurant calendar.
4. Reschedule or cancel each booking and confirm the notice and calendar event update.
5. Check **Edge Functions → Logs** for errors from either sender.

Reservation email delivery is asynchronous and best-effort: reaching the daily
limit queues reservation notices for the next Singapore day, while other Gmail
API failures do not roll back a booking. Keep OAuth secrets out of the website,
SQL source, and Git.
